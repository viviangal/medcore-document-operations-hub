# MedCore Document Operations Hub — Reflection

The application layer adds something that n8n alone does not provide particularly well: a simple interface for a human user to interact with the document-processing workflow. The original n8n workflow can receive a document, extract business information, store the result in Google Sheets and send an urgent notification, but it is primarily an automation workflow. The MedCore application turns those capabilities into a usable operational tool. A user can upload a document, immediately see the extracted information, search and filter the document log, open individual records, review documents, and see summary analytics without needing to open or understand n8n.

An important architectural decision was to keep the business logic inside n8n. The application does not call the AI model itself and does not decide document type, urgency, department, requested action or deadline. It sends documents to the existing workflows and presents the returned information. This keeps the automation logic in one place and prevents the application and workflow from developing different rules.

Human involvement is still necessary. AI extraction can organize and summarize information, but a person may still need to confirm that important information has been interpreted correctly and decide what action the organization should actually take. This is especially important for urgent, ambiguous or unusual documents. The review function provides a simple audit trail by recording who reviewed a document and an optional note. Humans are also required to respond to operational failures such as unavailable services, incorrect configuration or documents that contain no readable text.

At approximately 1,000 documents per day, I would expect the current architecture to encounter scalability limitations. Google Sheets is intentionally used as the source of truth for this project, but reading and updating a spreadsheet would become increasingly inefficient as the document log grows. The workflow also depends on several external services, including n8n, Google Drive, CloudConvert, Gmail and the AI service, so throughput, API limits and concurrent executions would become more important. At that scale I would also want queueing, stronger monitoring and more detailed operational logging.

If I were building the system again for production rather than as a course project, the main change I would make would be to introduce a proper backend and database from the beginning. I would use a database such as PostgreSQL for the operational records and keep credentials exclusively on a server-side backend. Google Sheets could still be used as a reporting or export destination, but it would no longer be the primary data store. This would improve scalability, security and reliability while preserving the n8n workflows as the automation layer.
